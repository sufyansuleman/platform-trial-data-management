## 0. What you are building and why

Build a **reference data-management and central-monitoring pipeline for a multi-site, multi-country, multi-domain adaptive platform trial**, in R.

This is a portfolio and demonstration project. It must run end to end on a laptop with no external services, using **entirely synthetic data that the pipeline itself generates**.

The design is informed by how large academic ICU platform trials are publicly described: many hospital sites across several countries, several clinical *domains* running simultaneously over a shared participant population, an electronic data capture (EDC) system feeding periodic exports, scheduled interim ("adaptive") analyses that require frozen data cuts, and central statistical monitoring of site data quality in place of visiting every site.

### Hard constraints — do not violate these

1. **Synthetic data only.** The repo must never contain, and the code must never expect, real patient data. All data is generated by `R/simulate/` from a seed.
2. **No real institution names anywhere in code, data, or docs.** Use fictional site names with realistic country codes (`DK-01 "Søndre Universitetshospital"`, `NL-02 "Maasstad Ziekenhuis Noord"` — invented). Realistic *structure*, invented *identities*.
3. **No claim of affiliation with any real trial, hospital, or research group.** The README must state plainly, near the top, that this is an independent educational project using synthetic data and is not affiliated with or endorsed by any real trial.
4. **No free-text fields in the synthetic data.** Everything is coded, dated, or numeric. This keeps the project trivially GDPR-safe and models good CDM practice.
5. **Determinism.** Same seed in, byte-identical data out. Everything downstream must be reproducible.

## 3. The simulated trial (config/trial.yml)

Model this shape:

- **Domains**: 3 running concurrently. Call them `FLUID`, `ANTICOAG`, `BUFFER`. Each has 2 arms, a 30-day primary outcome, and its own randomisation.
- **Multi-domain participation**: a participant may be randomised into more than one domain. Target roughly **1.2 randomisations per participant**. This is deliberate — it creates the cross-domain consistency problems that make this project interesting.
- **Sites**: 15 in country `DK`, then staggered initiation of 3 in `NL`, 3 in `SE`, 2 in `FI`, 2 in `IS` — the later countries starting 9–12 months after the first. Site initiation dates live in config.
- **Timeline**: 24 months of enrolment, monthly ramp-up, seasonal dips (summer, December).
- **Scale**: ~2,500 participants total. Large enough for signals to be visible, small enough to run in under two minutes.

### Cross-country realism — implement all of these

These are the details that separate this project from a generic validation exercise:

- **Date formats differ by country** in the raw export (`DD-MM-YYYY` vs `YYYY-MM-DD`), and the ingest layer must normalise and *log* what it normalised.
- **Units differ**: some sites report weight in kg, others in lb; creatinine in µmol/L vs mg/dL. Conversion happens in ingest, is logged, and is unit-tested.
- **Decimal separator**: some sites emit `,` instead of `.`.
- **Character encoding**: at least one site emits Latin-1 rather than UTF-8, mangling Nordic characters in site labels.
- **Local public holidays** (per country, in config) depress data-entry timeliness — so timeliness metrics must be interpretable against a country calendar, not a single global one.
- **Site initiation staggering** means a naive "completeness by site" table unfairly penalises new sites. The monitoring report must handle this — normalise by time-since-initiation, not calendar time.

## 4. Milestone 1 — MUST (this is the minimum viable project)

### 1.1 Synthetic data generator (`R/simulate/`)

Generate five forms per participant:

| Form | Grain | Key fields |
|---|---|---|
| `screening` | 1 per screened patient | screening date, eligibility flags, site |
| `randomisation` | 1 per participant per domain | randomisation datetime, domain, arm, site, allocation ratio in force |
| `daily_icu` | 1 per participant per ICU day (0–90) | alive flag, mechanical ventilation, vasopressors/inotropes, renal replacement therapy, ICU location |
| `outcome_30d` | 1 per participant per domain | vital status at 30d, hospital discharge date |
| `adverse_events` | 0..n per participant | AE code, onset date, seriousness, relatedness |

Simulate a **plausible clinical process**, not random noise: length of stay from a realistic distribution, life-support use correlated with severity and tapering over time, mortality around 30–40% at 30 days, AEs at a low base rate.

### 1.2 Defect injection (`R/simulate/inject_defects.R`)

This is the heart of the project. Inject known, **catalogued** data quality problems, and write the ground truth to `data/interim/injected_defects.parquet` so the validation engine's recall can be measured.

Inject at least:

- Missing required fields, at **site-specific rates** (one site is much worse than the others)
- Missing entire daily records in the middle of an ICU stay (a gap, not a truncation)
- Out-of-range values (weight 8 kg, heart rate 400)
- Impossible date sequences (discharge before admission, AE onset before randomisation)
- Duplicate participant IDs across two sites
- A participant randomised twice in the *same* domain
- Inconsistent vital status: alive on daily record day 12, but death date recorded as day 9
- Late data entry, worsening over time at one site (**drift** — the key signal)
- Terminal-digit preference at one site (values ending in 0 and 5 far too often)
- One site systematically under-reporting AEs
- Unit-conversion failures at one site (weight in lb submitted as kg)

Each injected defect is tagged with the rule ID it *should* trip.

### 1.3 Ingest (`R/ingest/`)

Read the raw CSV exports. Conform to schema. Normalise dates, units, encodings, decimal separators. **Emit a conformance log** listing every transformation applied, by site and field. Fail loudly on anything not covered by an explicit rule — never silently coerce.

### 1.4 Validation engine (`R/validate/`)

**The engine is generic; the rules are data.** Rules live in `config/rules/*.yml`. This is the single most important design decision in the project — it means a clinician or trial manager can review and propose rules without reading R code.

Each rule:

```yaml
- id: TMP-004
  name: ae_onset_before_randomisation
  scope: adverse_events
  severity: critical        # critical | major | minor | informational
  description: >
    Adverse event onset must not precede the participant's first
    randomisation datetime in any domain.
  rationale: >
    An AE preceding randomisation is not attributable to the trial
    intervention and indicates a data entry or linkage error.
  expression: ae_onset_date >= first_randomisation_date
  action: query
```

The engine returns a **findings table**, one row per violation:
`finding_id, rule_id, severity, site_id, country, participant_id, domain, form, field, observed_value, detected_at, data_version`

Critically: **the output is a findings dataset, not a pass/fail.** The point is to tell someone what to fix.

Then measure yourself: compare findings against `injected_defects` and report **recall per defect type** in a table in the README. Be honest about what the rules miss.

### 1.5 Derived endpoint (`R/derive/`)

Implement **days alive without life support at 30 days**:

> Number of days within the first 30 days after randomisation on which the participant was alive AND free of all of: invasive mechanical ventilation, vasopressor/inotropic support, and renal replacement therapy. Death within 30 days scores 0.

This is the number every adaptive stopping decision would read. Treat it accordingly.

**Write adversarial unit tests first**, covering at minimum:

- Death on day 0, day 1, day 29, day 30, day 31
- Life support for part of a day (define the convention explicitly in `docs/decisions.md` and test it)
- Missing daily records in the middle of the window — is that "not on support" or "unknown"? Decide, document, test. Defaulting missing to "free of support" silently inflates the endpoint; this is exactly the kind of bug that would move a trial decision.
- Participant transferred between ICUs mid-stay
- Discharged alive on day 10 and never readmitted
- Readmission to ICU on day 20 after discharge on day 10
- Life support starting exactly at the 30-day boundary
- Conflicting records for the same participant-day from two sources

Include a short section in the README explaining *why* this function has more tests than anything else in the repo. That reasoning is the point.

### 1.6 Site monitoring report (`reports/site_monitoring.qmd`)

One parameterised Quarto document, rendered once per site:

```r
for (s in sites) quarto::quarto_render(
  "reports/site_monitoring.qmd",
  execute_params = list(site_id = s),
  output_file = paste0("site_", s, ".html")
)
```

Contents:

- **Completeness** by form and by visit, as a **trend over the last 6 months**, not a single number
- **Timeliness**: median days from event to entry, trended, adjusted for that country's holiday calendar
- **Open findings** by severity, with participant IDs so the coordinator can act

- A plain-language "what to do this week" list at the very top

Design rule: **the actionable list comes first, the charts come second.** A monitoring report is a work instruction, not a dashboard.

## 5. Milestone 2 — SHOULD

### 2.1 Query lifecycle (`R/query/`)

Findings become **queries** with a real lifecycle, not just a list:

`raised → sent_to_site → answered → closed` — plus `reopened` when the answer doesn't resolve it.

Track **query ageing**: days open, banded (0–7, 8–30, 31–90, >90). Simulate site response behaviour with different responsiveness per site, so ageing distributions actually differ.

Why this matters: twenty open queries is normal. Twenty open queries averaging 90 days old means nobody at that site is reading them. **Ageing is the signal, not count.** Make the report say so.

### 2.2 Data cuts and freezes (`R/cut/`)

A cut is: *all participants who have completed 30-day follow-up as of date D*, while enrolment continues past them.

`make_cut(as_of_date)` must produce:

- The frozen dataset (Parquet)
- A **manifest**: cut ID, as-of date, creation timestamp, participant count by site and domain, row counts by form, **SHA-256 of every file**, package versions, git commit SHA, rule-set version
- A human-readable summary (`data_cut_summary.qmd`)

Then prove it: a test that regenerates a historical cut from the same inputs and asserts hash equality. Put this in the README as *"can you regenerate the exact dataset a committee saw a year ago? Yes — here is the test."*

### 2.3 Post-lock change detection

Simulate successive EDC exports where **a value inside an already-frozen cut is later edited at the site**.

Detect it. Report it. This is what an audit trail is for, and almost no portfolio project does it. A retrospective edit to locked data is a serious finding in a regulated trial — flag it as `critical` and surface it prominently in the central report.

## 6. Milestone 3 — NICE TO HAVE

### 3.1 Risk-based central monitoring (`R/monitor/`)

Statistical signals that identify sites needing attention without visiting them:

- **Terminal-digit preference**: chi-square test on last digits of continuous measurements
- **Variance anomalies**: site-level variance far below pooled (data too clean = possibly fabricated or carried forward)
- **AE under-reporting**: observed vs expected AE rate given case-mix, as a funnel plot with control limits
- **Enrolment anomalies**: unusual timing patterns, clustering of randomisations
- **Digit/date rounding**: excess of month-start dates

Present as a **funnel plot** with 95% and 99.8% limits — the standard presentation for site-level comparison, and it correctly stops you over-reacting to small sites.

### 3.2 Cross-domain consistency (`config/rules/cross_domain.yml`)

For participants in more than one domain: baseline characteristics must agree, the death date must be identical across domains, and 30-day windows overlap but are anchored to *different* randomisation dates. Check all of it.

### 3.3 Simulated allocation-update reconciliation

Model the loop where an interim analysis produces new allocation probabilities that must reach the EDC. Then reconcile: does the **realised** allocation ratio at each site match what was **specified** for that period? Flag drift.

This is a genuinely under-appreciated failure mode — nothing errors, patients are just randomised wrongly.

## 1.2 SAE reconciliation (`R/reconcile/`)

Real trials keep serious adverse events in **two places**: the clinical database (entered
by sites on the AE form) and a separate safety/pharmacovigilance record (expedited
reporting). These drift apart, and reconciling them is a core, recurring data management
task.

Implement:

- Simulate a second `safety_db` export with deliberate discrepancies: SAEs present in one
  source and not the other, mismatched onset dates, mismatched seriousness criteria,
  differing outcome coding
- `reconcile_sae()` produces a discrepancy table: `participant_id`, `sae_id`, `field`,
  `clinical_value`, `safety_value`, `discrepancy_type`
- Discrepancies feed the query system like any other finding, at `critical` severity
- A reconciliation section in the central monitoring report

Add a short paragraph to `docs/decisions.md` explaining why SAE reconciliation cannot be
skipped even when both sources "look fine".

# PART 2 - Bayesian adaptive analysis layer: OUT OF SCOPE

This project covers the **data management** side of the trial only. The Bayesian
adaptive analysis layer originally specified here has been removed from scope: the
statistical analysis plan, the interim analysis engine, the prior machinery and the
design simulation.

What that boundary means in practice, and why it is a real boundary rather than an
omission:

- The pipeline produces a **frozen, verifiable data cut** and stops there. Section 2.2 of
  Milestone 2 remains fully in scope, because producing a dataset an analysis can be run
  on, and proving it can be regenerated exactly, is a data management responsibility.
- **Allocation reconciliation remains in scope.** It appears in this specification twice:
  once as section 3.3 of Milestone 3, which is data management, and once inside the
  analysis addendum. The data management question is whether the allocation probabilities
  that were specified actually took effect at each site, and answering it requires no
  analysis at all.
- The analysis layer is not stubbed or half-built. It was implemented and then removed, so
  that what remains reads as a complete data management project rather than an incomplete
  larger one. The work is in the git history up to commit 0ccf9e9 for anyone who wants it.

PART 1 above, the data management plan, remains fully in scope.
