# Standard operating procedure: producing a data cut

**Status.** This procedure is written before the implementation, deliberately. A cut
specification produced after the fact describes whatever the code happened to do; one
written first is something the code can be held to. `R/cut/` is built against this
document in Milestone 2, and the test suite asserts the guarantees stated here.

---

## 1. What a data cut is

A **cut** is a frozen, immutable dataset containing every participant who has completed
30-day follow-up as of a stated date, produced while enrolment continues past them.

It is not a copy of the database. It is a defined subset, taken at a defined moment,
recorded in enough detail that it can be regenerated byte for byte later.

### Why the seam matters

Every analysis of this trial runs on a cut and never on the live database. Three
reasons:

1. **The live database changes underneath you.** A site can edit a value at any time. An
   analysis run twice on live data can give two answers, and neither is wrong.
2. **A committee's decision must remain auditable.** When a data monitoring committee
   stops a domain for superiority, the question "what did they actually see?" must have an
   exact answer years later.
3. **Late follow-up creates bias if handled carelessly.** Including participants who
   happen to have complete data, rather than all who have reached 30 days, selects on the
   outcome.

## 2. Inclusion rule

A participant-domain record enters the cut when:

- The participant was randomised into that domain on or before `as_of_date - 30 days`, so
  their 30-day window has closed; **and**
- The randomisation record carries a randomisation date and time, without which no window
  can be anchored.

Records are included **whether or not their data is complete**. A participant whose daily
records are missing is in the cut with an incomplete endpoint and an explicit
`unknown_days` count. Excluding them because their data is untidy would select the
analysis population on data quality, which correlates with site, which correlates with
everything else.

Participants still within their 30-day window are excluded entirely, not included with a
partial outcome.

## 3. What a cut contains

| Artefact | Format | Purpose |
|---|---|---|
| Conformed forms | Parquet, one file per form | The frozen data |
| Derived endpoints | Parquet | Days alive without life support, with completeness flags |
| Findings | Parquet | Every validation finding open at the moment of the cut |
| Manifest | JSON | Everything needed to identify and reproduce the cut |
| Human summary | HTML, rendered from `reports/data_cut_summary.qmd` | What a committee receives |

## 4. The manifest

Every cut carries a manifest recording:

- **Cut identity** - cut ID, as-of date, creation timestamp (UTC)
- **Contents** - participant count by site and by domain; row count by form
- **Integrity** - SHA-256 of every file in the cut
- **Provenance** - git commit SHA of the code, `renv.lock` hash, R version, versions of
  every package used, rule-set version
- **Data quality at the moment of freezing** - findings by severity, endpoint
  completeness, and the count of records that are not evaluable

The provenance block is what makes the cut reproducible rather than merely archived. A
dataset without the code version that produced it can be inspected but not regenerated.

## 5. Producing a cut

```r
cut <- make_cut(as_of_date = as.Date("2025-06-30"))
```

The function must, in order:

1. Run the pipeline to a conformed, validated state
2. Apply the inclusion rule
3. Derive endpoints for the included records
4. Write the Parquet files
5. Compute SHA-256 for each file written
6. Assemble and write the manifest
7. Render the human-readable summary

Steps 4 to 6 must not be reorderable: hashes are computed from the files as written, never
from the in-memory objects, because what a later reader verifies is the file.

## 6. Verifying a cut

```r
verify_cut(cut_id)
```

Recomputes the SHA-256 of every file and compares against the manifest. Returns the list
of files whose hash disagrees. **Any disagreement means the cut has been altered since it
was frozen** and it must not be used for analysis.

Any consumer of a cut is expected to call `verify_cut()` before using it and to refuse to
proceed if it fails. That refusal is the point: an analysis run on a silently modified cut
is worse than no analysis, because it carries the authority of a frozen dataset without the
substance of one. Producing that guarantee is where this repository's responsibility ends
and the analysis team's begins.

## 7. Reproducing a historical cut

```r
reproduce_cut(cut_id)
```

Regenerates the cut from the recorded provenance and asserts hash equality against the
stored manifest. The test suite runs this for a stored cut, so the claim is checked on
every commit rather than asserted in a README.

This is the strongest guarantee the repository makes: **given a cut ID, the exact dataset
a committee saw can be regenerated and proven identical.** It holds because the pipeline
is deterministic from a seed and because the manifest records every version the output
depends on.

### What would break it

- A change to `config/trial.yml` that alters the simulation. The manifest records the
  configuration hash so this is detected, not silently absorbed.
- A package upgrade that changes numerical output. The manifest records package versions;
  `renv.lock` restores them.
- Any non-deterministic step - an unseeded random draw, a timestamp inside the data, a
  hash of an unordered set. None may be introduced.

## 8. Retrospective edits to frozen data

A site can edit a value that is already inside a frozen cut. The cut itself does not
change - it cannot, or it would not be a cut - but the discrepancy must be **detected and
reported**, because an analysis has already been run on the superseded value.

Successive exports are compared against the frozen cut. Any value that differs is raised
as a `critical` finding identifying the participant, the field, the frozen value, the new
value and the cut affected. This is implemented in Milestone 2.3 and surfaced
prominently in the central monitoring report.

A retrospective edit to locked data is a serious finding in a regulated trial. It is not
necessarily misconduct - it is usually a site correcting a genuine error - but it means a
committee made a decision on a value that no longer exists, and somebody has to decide
whether that changes anything.

## 9. Who may do what

| Role | May |
|---|---|
| Data manager | Produce a cut, verify a cut, reproduce a cut |
| Statistician | Read a cut, run the pre-specified analysis on it. Analysis is outside this repository's scope; the cut is the handover point |
| Site investigator | Neither produce nor read cuts; they see their own site's data only |
| Coordinating centre | Request a cut at a specified as-of date |

No role may modify a cut once written. Correcting an error means producing a **new** cut
with a new ID, recording why in the change log, and leaving the original in place.
